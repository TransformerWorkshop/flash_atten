## Phenomenon
- `tb_gemm`/`tb_gemm_col` 初版中，`m_group_data` 首次输出为全 0，`m_group_idx` 在检查时出现不前进或顺序错位，导致用例失败。
- `modelsim` 编译入口执行失败：`/bin/sh: vsim: command not found`。

## Root Cause
- `GEMU` 的 `fifo_m_valid` 由 `acc_done` 直接驱动；当 `num_acc=0`（上电初值）时会向输出 FIFO 预填 0。
- `GEMM` 在 `STATE_COLLECT` 启动阶段对 PE 输出立即 `ready`，把历史 0 结果误当作本轮计算结果收集，提前进入 `STATE_STREAM`。
- testbench 对“握手采样时刻”处理不严谨，导致组间检查有一拍错位风险。

## acc_done 历史遗留问题说明
- 设计历史上 `acc_done` 被定义为组合条件：`acc_done = (acc_cnt == num_acc)`，并直接驱动 `fifo_m_valid`。
- 在 `start` 之前，`acc_cnt` 复位为 0，而 `num_acc` 常常也为 0（默认值），导致 `acc_done` 在“尚未开始计算”时就为真。
- 结果是 GEMU 输出 FIFO 会提前写入“历史 0 结果”，形成脏数据。
- 当上层（如 GEMM）进入收集阶段时，如果没有额外门控，就可能先消费到这些历史 0，造成：
  - 提前判定收集完成；
  - 输出组数据为 0 或顺序错位；
  - 与真实本轮乘加结果不一致。
- 该问题最初通过 GEMM 侧门控临时规避；后续已在 GEMU 内部完成修复并移除上层冗余门控。
